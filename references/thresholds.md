# Analysis Thresholds

The bands Stage 3 and Stage 3.5 use to classify a measured value into a severity.
Read this before interpreting `analysis.json`: a finding states a severity, and
this file is where that severity's meaning lives.

**The tables below are generated from the code** by
`scripts/generate_thresholds_doc.py`, and `tests/test_thresholds_doc.py` fails if
they drift. That is unusual for a file in `references/` — the others here are
hand-written and merely checked — and it is deliberate. This file is not
documentation the agent may skim; it is *input* the agent is instructed to apply,
so a band described here that `classify_value` cannot return does not read as a
stale comment. It reads as a severity that never arrived, which is a pass. Edit
the registry in `analyze_metrics.py` and re-run the generator.

No scores here. An earlier version of this file specified a weighted 0-100 pillar
formula for a scoring engine that was deliberately removed — a weighted score is
judgment wearing the costume of a measurement, and the agent owns judgment.
The single remaining copy of that formula is SKILL.md's **Scoring Methodology**,
which the agent computes on request and shows the arithmetic for.

## Severity Levels

| Level | Color | Meaning | Action |
|-------|-------|---------|--------|
| CRITICAL | Red | Immediate risk to availability or data | Fix within 24 hours |
| HIGH | Orange | Significant risk or degradation | Fix within 1 week |
| MEDIUM | Yellow | Sub-optimal but not immediately dangerous | Plan remediation |
| LOW | Blue | Minor improvement opportunity | Backlog |
| HEALTHY | Green | Within acceptable range | No action needed |

## A Note on Units

Every threshold below is graded against a value in the unit stated in its
heading, and each is registered in `analyze_metrics.py` with that unit declared
(`ThresholdLevel.unit`), so a mismatch is a startup error rather than a plausible
finding.

Three count metrics — **Evictions**, **NewConnections**, and **ThrottledCmds** —
need a conversion to get there. CloudWatch delivers them as a `Sum` over the
collection period, which is 300 seconds, so a raw datapoint is a five-minute
total. Their thresholds are per minute, because that is the rate an operator
reasons about, so Stage 3 derives a `<Metric>PerMinute` series
(`sum / (resolution_seconds / 60)`) and grades that. The raw series is kept
alongside it for the models that legitimately want a period total.

The conversion divides by Stage 2's reported resolution rather than a constant,
so a run collected at a different period stays correct. Grading the raw Sum
against a per-minute number is the defect this replaced: `NewConnections`' MEDIUM
boundary of 1000/min was firing at roughly 200/min.

## Trend-Based Thresholds

Beyond point-in-time values, Stage 3 fits a linear regression to daily averages over the 14-day window. A trend is only reported when R² > 0.4 *and* the slope clears the minimum below — a confident fit on an operationally irrelevant slope is not a finding.

Rising is the concerning direction for every metric here except `CacheHitRate`, where it is declining.

The metrics named here are the **raw** CloudWatch series, not the derived ones the point-in-time bands above grade. `Evictions` is the case to watch: its threshold band is per minute, but its trend is fitted to the per-period Sum, so the two rows are about series with different units and the same name.

| Metric | Reported when | Severity |
|--------|---------------|----------|
| DatabaseMemoryUsagePercentage | rising > 2 percentage points per week | MEDIUM, escalating to HIGH above 5 percentage points per week |
| BytesUsedForCache | any rising trend | MEDIUM |
| CurrItems | any rising trend | MEDIUM |
| CurrConnections | any rising trend | MEDIUM |
| Evictions | any rising trend | MEDIUM |
| CacheHitRate | declining > 5 percentage points per week | MEDIUM, escalating to HIGH above 10 percentage points per week |
| ReplicationLag | any rising trend | MEDIUM, escalating to HIGH above 1 second per week |
